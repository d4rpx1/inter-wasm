 Same .wasm files, same inputs, 10k warmup + 100k measured calls
==============================================================

│ add_with_local(5) → 10      │   0.237 µs     │   0.013 µs     │    ~18×      │

Instruction counts (one call, from ExecutionStats):

  add_with_local   dispatches=  5   operandReads=  6   operandWrites=  5
  simple_loop      dispatches=137   operandReads=136   operandWrites=114
  fibonacci        dispatches=183   operandReads=190   operandWrites=160

  operandOps per dispatch ≈ 1.8–2.2  (most instructions need 2 pops + 1 push)

──────────────────────────────────────────────────────────────
 WHY the slowdown grows with instruction count:
──────────────────────────────────────────────────────────────

  Node.js / V8 JIT:
    → Compiles .wasm to native x86 at load time
    → Result: pure Nutzlast (actual computation only)
    → add, compare, branch = ~1–3 native instructions each

  Java tree-walking interpreter:
    → For every single instruction:
        DISPATCH        typeSwitch(invokedynamic) + tableswitch
        OPERANDENZUGRIFF  invokevirtual popI32() × N + pushI32() × M
        NUTZLAST        iadd / isub / ... (the actual work)
    → Overhead is PER INSTRUCTION, so slowdown scales with dispatch count

  add_with_local:  5 dispatches  → ~18× slower  (base interpreter startup)
  simple_loop:   137 dispatches  → ~52× slower  (linear scaling)
  fibonacci:     183 dispatches  → ~256× slower (+ V8 fib JIT is extremely fast)
